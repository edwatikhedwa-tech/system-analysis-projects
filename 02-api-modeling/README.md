# Моделирование профиля API — оформление страховки для питомца

Проектирование нового REST API: от Job Story до операций, ресурсов и структуры ответа. Отдельно — определение границ между новым API и уже существующими сервисами.

> Учебный кейс курса «Системный аналитик». Текст задания не публикуется — здесь только моя работа.

---

## Задача

В приложении для владельцев домашних животных появляется новая цифровая возможность — оформление страховки на питомца прямо в приложении: выбрать программу, добавить в корзину и оплатить онлайн.

**Моя роль:** системный аналитик — определить, какие действия пользователя нужно поддержать, что из этого уже покрыто существующими API, и спроектировать профиль только для того API, которого ещё нет.

## Что сделано

### 1. Дополнил Job Story

> **Так как** у меня активный и любопытный питомец,
> **я хочу** выбрать и купить страховку прямо в приложении — добавить в корзину и оплатить онлайн,
> **чтобы** быть финансово защищённым в случае травм или болезней и не тратить время на визиты в офис и заполнение сложных форм.

### 2. Определил действия и их шаги

| Цифровая возможность | Действие | Шаг действия | Участник | Описание |
| :--- | :--- | :--- | :--- | :--- |
| Оформить страховку | Ознакомиться со страховками | Просмотреть данные страховок | Пользователь | Загрузить весь список страховок с условиями и ценами одним запросом |
| Оформить страховку | Положить страховку в корзину | Добавить страховку в корзину | Пользователь | Отправить ID выбранной страховки в сервис корзины |
| Оформить страховку | Оплатить страховку | Оплатить заказ | Пользователь | Завершить покупку через интернет-эквайринг |

### 3. Определил границы API

Ключевой шаг: не всё, что делает пользователь, требует нового API.

| Шаг действия | Кто обслуживает | Решение |
| :--- | :--- | :--- |
| Просмотреть данные страховок | **Новый API** | Запросить данные в формате JSON с полным описанием сервиса и страховок |
| Добавить страховку в корзину | Существующий API | Взаимодействие с **Shopping Cart** |
| Оплатить заказ | Существующий API | Взаимодействие с **Payment** |

Из трёх шагов сценария новой разработки требует только один. Два других переиспользуют работающие сервисы — страховка для них такой же товар, как любой другой.

### 4. Смоделировал профиль нового API

| Параметр | Значение |
| :--- | :--- |
| **Операция** | `получитьКаталогСтраховок()` |
| **Описание** | Получить полный список страховок с условиями, ценами и описанием сервиса |
| **Участники** | Пользователь |
| **Ресурсы** | Страховка, Каталог |
| **Параметры** | отсутствуют |
| **Возвращает ресурс** | КаталогСтраховок |
| **Свойства** | безопасная (только чтение), синхронная |

**Структура ответа:**

```json
{
  "description": "Помощь ветеринара 24/7...",
  "plans": [
    {
      "id": "ins-001",
      "price": 35000,
      "currency": "RUB",
      "period": "год",
      "animalType": "cat",
      "features": [
        "Круглосуточные консультации",
        "Ежегодная вакцинация"
      ]
    }
  ]
}
```

## Выводы

- **Границы API определяются до его проектирования, а не после.** Разбор по шагам показал, что два из трёх шагов сценария закрываются существующими сервисами. Спроектировать «API оформления страховки» целиком означало бы продублировать корзину и платежи.
- **Операция «безопасная и синхронная» — не формальность.** Эти два свойства сразу отвечают на вопросы про кэширование, повторные вызовы и поведение при таймауте. Аналитик отвечает на них в профиле, иначе на них ответит разработчик по своему усмотрению.
- **Пример ответа полезнее описания полей.** Разработчик и тестировщик видят реальную структуру: вложенность, типы, формат цены и валюты. Спорить об именовании полей проще над конкретным JSON, чем над таблицей.
- **Отсутствие параметров у операции — тоже решение.** Каталог отдаётся целиком одним запросом: страховых программ немного, фильтрация выполняется на клиенте. При росте каталога это первое, что придётся пересмотреть.
